# Internationalization (Bangla) — Architecture & Conventions

Bangla (bn) localization of the frontend. Planning approved 2026-07-09. Terminology lives in [I18N-GLOSSARY.md](./I18N-GLOSSARY.md) — read it before translating anything.

## Decisions (locked)

| Decision | Choice | Why |
|---|---|---|
| Library | `next-intl`, **without i18n routing** (no `/bn/` URL prefix) | App is auth-gated SaaS with custom-domain tenants; URL prefixes would touch `proxy.ts`, deep links, and tenant routing for no benefit |
| Locale source of truth | `user.locale` profile field (`"en" \| "bn"`, default `"en"`) | Cross-device persistence |
| SSR locale | `NEXT_LOCALE` cookie mirrors the profile field | Server components read the cookie → correct language on first paint, no flash |
| Reconciliation | On login / `/me` fetch, profile wins; cookie is updated to match | |
| Pre-auth pages | Cookie only (login-page `EN \| বাং` toggle writes cookie); adopted into profile after signup/login | |
| Digits | Western digits (0-9) with lakh/crore grouping; currency ৳ | BD business-software norm; Bengali-numeral toggle deferred |
| Dates | date-fns `bn` locale via central formatters | |
| CSV export headers | Stay English | Import engine matches on headers; translating breaks round-trip |
| Backend error messages | Deferred (shown as-is, English) | Needs error-code contract; Phase 5 |
| Receipt/document language | Future **org-level** setting, separate from UI locale | Printed docs are the shop's choice, not the viewer's |
| Test locale | English; i18n provider in test setup | Existing `getByText("...")` assertions keep working |

## Language switcher UI

1. **Avatar/user dropdown** (primary): "Language / ভাষা" → `English` / `বাংলা`. Selecting: PATCH profile + set cookie + `router.refresh()`. No reload, no logout.
2. **Settings → Preferences**: same control, discoverable home.
3. **Login page**: small `EN | বাং` toggle, cookie-only.

Languages always shown in their own script. No flag icons.

## Message files & namespaces

```
messages/
  en/
    common.json      # chrome shared app-wide (see seeding rules below)
    auth.json        # app/(auth), components/login, components/setup
    layout.json      # sidebar, nav, kbar, user menu
    dashboard.json
    products.json    # incl. brands, categories, units, variants, combos
    inventory.json   # stock, adjust, transfers, batches
    sales.json
    purchases.json
    customers.json
    suppliers.json
    accounts.json
    reports.json
    settings.json    # incl. users, roles, locations, taxes, discounts, domains, profile, billing
  bn/
    (same files)
```

Rule: **file location must be guessable from component location.** `components/purchases/*` → `purchases.json`. Small catalog features (brands, categories, units, variants) fold into `products.json`; org-admin features fold into `settings.json` — they are too small (<30 keys each) to justify separate files.

## Key naming

- Semantic keys, never English sentences as keys.
- Pattern: `section.key`, camelCase, inside the namespace file: `useTranslations("purchases.orders")` → `t("markReceived")`.
- Max 3 levels deep (`namespace.section.key`). No 4th level.
- Name by meaning, not by English wording: `deleteConfirmBody`, not `areYouSureYouWantToDelete`.
- Interpolation via ICU: `"received {count} of {total} items"`. Never concatenate translated fragments.

## common.json rules

Share only true app chrome. When unsure, duplicate into the feature namespace — merging duplicates later is cheap; un-sharing a wrongly shared key is a 55-page hunt.

Seed list (from the 2026-07-09 automated scan of 481 files / ~1,950 unique strings; file-spread counts in parens):

- **Actions**: Cancel (28f), Delete (15f), Edit (11f), Close (6f), Save, Search (6f), View Details (4f)
- **States**: `common.status.*` — Active (24f), Inactive (22f), Pending, Draft, Cancelled (11f), Expired, Default; `common.paymentStatus.*` — Paid (14f), Due (15f), Partial, Refunded
- **Fields**: Name, Email (12f), Phone, Address, Notes, Description, Type, Date, Reason, Status (30f)
- **Empty/loading**: No data available (10f), Loading…, All statuses (12f), All types
- **Dates**: Today, Created Date, Updated Date, Select date, Select date range

Domain terms with 3+ file spread (Product, Supplier, Discount, Tax, Total, Subtotal…) do **not** go in common — they belong to their feature namespace; the glossary keeps them consistent across files.

## Shared-component strategy

`ui/` components (DataTable, dialogs, PageHeader, ExportDialog, PrintMenu…) had ~322 string occurrences in the scan. They must not import feature namespaces:

- Default labels (pagination, "No data available", sort tooltips) come from `common`.
- Feature-specific text (column headers, dialog titles) is passed in **already translated** by the caller. Component APIs keep taking strings; no key-passing across component boundaries.

## Central formatters (Phase 1, valuable standalone)

`lib/format.ts` — the only place `Intl`/date-fns locale logic lives:

- `formatCurrency(amount)` → ৳ + lakh/crore grouping (replaces ~40 scattered `toLocaleString` calls)
- `formatNumber(n, opts)`
- `formatDate(d, style)` / `formatDateTime(d)` (replaces ~49 raw `format()` calls)

Migrate all call sites to these **before** locale switching lands, as its own PR.

## QA checklist per translated page

- [ ] No hardcoded English left (search literal strings in the diff)
- [ ] Glossary terms match glossary exactly
- [ ] bn layout: no overflow/clipping in buttons, table headers, badges (Bengali glyphs are taller; text often longer)

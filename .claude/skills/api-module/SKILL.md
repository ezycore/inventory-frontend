# API Module Skill (Frontend)

How a resource is wired on the frontend: one `api.ts` (request shapes), one `hooks.ts` (TanStack
Query, usually from `createResourceHooks`), centralized query keys, and a barrel export — all typed
off the **generated** backend types so a backend rename becomes a compile error here, not a silent
`undefined` in the browser.

> **The API contract is NOT documented here.** It is *declared* in the backend as Zod response DTOs,
> emitted to `docs/reference/openapi.json`, and generated into this repo's `types/api-generated.ts`.
> Read [`inventory-backend/.claude/skills/api-contract/SKILL.md`](../../../../inventory-backend/.claude/skills/api-contract/SKILL.md)
> before changing anything that crosses the wire. This file is the FE plumbing on top of that contract.

---

## 1. The four files of a resource

Every module under [`services/api/modules/<resource>/`](../../../services/api/modules) has:

| File | Holds |
|---|---|
| `api.ts` | a plain object of methods calling `apiClient` (`lib/api-client.ts`) — the request shapes |
| `hooks.ts` | TanStack Query hooks, usually `createResourceHooks(...)` from [`../query-helpers.ts`](../../../services/api/modules/query-helpers.ts) |
| `index.ts` | barrel re-export |
| (analytics/types as needed) | e.g. `inventory/analytics.types.ts` |

Then: add keys to [`services/api/query-keys.ts`](../../../services/api/query-keys.ts) and export the
module from [`services/api/index.ts`](../../../services/api/index.ts). That is the whole checklist —
it is in the repo's [`CLAUDE.md`](../../../CLAUDE.md) ("Adding a New Resource Module").

## 2. Type it off the backend — never hand-write the response

`types/api-generated.ts` is generated by `pnpm gen:api-types` from the backend OpenAPI spec. **Do not
edit it.** The single alias barrel is [`types/api.ts`](../../../types/api.ts) — map a backend schema to
a friendly name there (`Api`-prefixed where it clashes with a hand type, e.g. `ApiInventory`,
`ApiVariant`). **Import response types from `@/types/api`, never reach into `api-generated` directly.**

In `api.ts`, type the envelope with the generated type:

```ts
getAll: (f?) => apiClient.get<ApiResponse<PaginatedResponse<ProductListItem>>>("/products", ...)
getById: (id) => apiClient.get<ApiResponse<ProductDetail>>(`/products/${id}`, ...)
```

`createResourceHooks<TDetail, CreateDto, UpdateDto, TList = TDetail>` is **generic-preserving** — the
type flows through `getAll`/`getById` to the hook and out to components, so a component reading a field
the backend doesn't send fails to compile. `TList` is separate because the list is often a slimmer
projection than the detail. A method typed `ApiResponse<any>` still satisfies the factory (`any` is
assignable both ways), so modules tighten off `any` **one at a time** — that is the migration lever.

**When the backend response contract changes:** `pnpm gen:api-types` → `pnpm typecheck` and fix the
breaks (that is the drift surfacing) → commit the regenerated `api-generated.ts`. The gate
`pnpm verify:api-types` fails CI if the committed file is stale; `pnpm verify` runs that + `docs:verify`
+ `typecheck`.

## 3. Query keys — centralized, never inlined

All keys live in [`services/api/query-keys.ts`](../../../services/api/query-keys.ts) (re-exported from
`lib/query-keys.ts` for back-compat). A resource exposes `all()` / `list()` / `detail(id)` (and
`bySlug` where relevant). **Never inline a key array** — always `queryKeys.<resource>.*`, or invalidation
misses.

### Cross-resource invalidation (the recurring bug)

When resource A's data appears on resource B's list (a category name on the products table), mutating A
must refetch B. Wire it once:

```ts
createResourceHooks({ ..., relatedQueryKeys: [queryKeys.products.all()] })
```

in the *mutated* resource's `hooks.ts` (see `categories`, `brands`, `units` → they all list
`queryKeys.products.all()`). A stale name after an edit is almost always a missing `relatedQueryKeys`.

## 4. The client + query defaults (don't re-implement)

- **`apiClient`** (singleton, [`lib/api-client.ts`](../../../lib/api-client.ts)) attaches
  `Authorization: Bearer <token>` and the `X-Active-Location` header, and on 401 clears auth and
  redirects to `/login`. Every call goes through it — never `fetch` a protected endpoint directly.
- **QueryClient** ([`lib/react-query.ts`](../../../lib/react-query.ts)): staleTime 1 min, gcTime 10 min,
  no refetch on focus, no retry on 4xx except 408/429. Don't hand-tune per-hook unless a resource truly
  needs it.
- CSV import: spread `createImportApi("/<resource>")`
  ([`services/api/modules/import-api.ts`](../../../services/api/modules/import-api.ts)) — see the
  `import-export` skill.

## 5. Pitfalls / debugging

| Symptom | Cause | Fix |
|---|---|---|
| List stale after editing a related resource | missing cross-invalidation | add `relatedQueryKeys: [queryKeys.<list>.all()]` to the mutated resource's hooks |
| `Page 1 of undefined` | list envelope changed / dropped pagination meta | keep `{ success, data, message, meta }`; list `data` is `PaginatedResponse<T>` |
| Response field is `any` in a component | module still typed `ApiResponse<any>` | alias the real type in `types/api.ts` and point the api method at it; regen if the DTO is missing |
| `verify:api-types` fails in CI | backend contract changed, FE types not regenerated | `pnpm gen:api-types`, commit `api-generated.ts` |
| Field you expect is `undefined`, no type error | backend never sends it (or it has **no DTO** yet) | check the backend DTO/projection first — the type is the contract |
| Wanted a `/api/...` path but got 401 | wrong base or missing auth | use `apiClient`; base has no `/v1` |

## 6. Things NOT to do

- Don't edit `types/api-generated.ts` — regenerate it.
- Don't import from `@/types/api-generated` — go through `@/types/api`.
- Don't hand-write a response interface for something the backend already returns — alias the generated
  type. A hand copy is the exact drift this system removes.
- Don't inline query keys or re-tune the QueryClient per hook.
- Don't bypass `apiClient` (you lose auth, active-location, and 401 handling).
- Don't keep an `any` when a DTO exists — tighten it; if the DTO is missing, prefer fixing the backend
  DTO over hand-typing (leave a `TODO(backend)` if you must).
